# 本地缓存存储引擎（cache-storage-engine-java）

基于 Spring Boot 的可对外访问本地缓存存储引擎：带 TTL 的键值读写与批量操作、
按命名空间隔离的键空间与独立容量上限、容量上限下的确定性拒绝（不淘汰存活数据）、
多线程并发安全、WAL 持久化与崩溃恢复。

## 快速开始

```bash
mvn spring-boot:run          # 启动服务（默认随机端口，可用 server.port 指定）
mvn test                     # 运行全部测试
```

### REST 接口

所有端点都接受可选空间：GET/DELETE/stats 用查询参数 `?namespace=<名>`，
POST 用请求体字段 `"namespace"`。**缺省时落入默认空间 `default`，与旧版行为完全一致**
（旧请求体不带 `namespace` 字段可照常反序列化）。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/cache/{key}?namespace=` | 读取单键（可指定空间） |
| POST | `/api/cache` | 写入单键，body: `{"key","value","ttlMillis","namespace"?}` |
| DELETE | `/api/cache/{key}?namespace=` | 删除单键（可指定空间） |
| POST | `/api/cache/batch-get` | 批量读，body: `{"keys":[...],"namespace"?}`，逐键返回命中值或失败原因 |
| POST | `/api/cache/batch-put` | 原子批量写，body: `{"entries":{...},"ttlMillis","namespace"?}` |
| POST | `/api/cache/batch-delete` | 批量删，body: `{"keys":[...],"namespace"?}`，逐键返回结果状态 |
| POST | `/api/cache/purge-expired` | 主动清理过期键（所有空间），返回回收数量 |
| GET | `/api/cache/stats?namespace=` | 不带参数：全引擎聚合统计；带参数：该空间独立统计 |
| GET | `/api/cache/namespaces` | 当前已知的空间名列表 |

失败原因通过 **HTTP 状态码 + 响应体 `code`** 双重区分：

| 失败原因 | HTTP | code |
|---|---|---|
| 键不存在 | 404 | `NOT_FOUND` |
| 键已过期 | 410 | `EXPIRED` |
| 容量不足 | 507 | `CAPACITY_FULL` |

## 空间模型（命名空间隔离）

- **空间即隔离边界**：每条数据归属于一个命名空间；不同空间下**同名键是两份互不影响
  的数据**——读、写、删、批量读写、统计都按空间各自独立。
- **默认空间**：不指定空间的调用（旧 API / 旧请求体）一律落入 `default` 空间，
  行为与旧版完全一致；旧版 v1 WAL 恢复出的数据也全部归入默认空间。
- **空间无需预创建**：首次写入自动存在；空间名为非空白字符串（空白名直接参数异常，
  不会静默落库）。
- **独立容量、互不挤占**：每个空间有各自的存活条目上限（见配置项）。某空间写满时，
  只有该空间的新写入被拒绝（`CAPACITY_FULL`），其它空间照常读写；空间之间绝不互相
  挤占容量。
- **不静默丢数据**：任何空间都不会为了腾位淘汰未过期数据；写入失败原因
  （`CAPACITY_FULL`）与键不存在（`NOT_FOUND`）、已过期（`EXPIRED`）始终可区分。
- **极端情况的确定结果**：批量写入的不同新键数量超过所属空间总容量、或空间容量被
  配置为 0 时写入新键——确定性地**整体拒绝**（`CAPACITY_FULL`），已有数据完全不变。
- **容量只约束新写入**：重启恢复出的数据即使超过空间上限也完整保留（输出告警日志），
  后续新写入仍按上限判定。

## 一致性模型

- **线性化**：每个对外操作（get/put/delete/批量操作）对键空间状态构成一个线性化点。
  写路径（put/delete/批量写/清理/压缩）在单把引擎级写锁下串行执行——**跨空间操作
  同样互斥**，不存在锁顺序环，**无死锁**。
- **无锁读路径**：读不加锁。写线程用"整体替换条目对象"的方式发布更新
  （`ConcurrentHashMap` 保证安全发布），读者只能看到更新前或更新后的完整对象，
  不会读到撕裂状态；单写者递增序列下读者不会观测到回退。
- **无丢失更新 / 无计数漂移**：每个空间的存活计数只在写锁内递增；递减可能发生在
  无锁读路径的惰性过期 CAS 回收（CAS 保证同一条目只递减一次）；hits/misses/
  expirations/evictions 等计数均为原子变量。并发容量边界按空间各自精确
  （放满即拒，不多不少）。
- **过期回收的并发安全**：读线程惰性回收过期条目时使用 CAS（`map.remove(key, entry)`），
  只有条目仍是同一个过期对象时才删除，绝不误删并发写入的新值。
- **批量写原子性**：`batch-put` 先校验全部键值、回收过期、按所属空间核算容量，
  全部通过才生效；任一条件不满足则**整体拒绝**，已有数据与计数完全不变。

## 过期与淘汰规则

1. **过期判定**：`now >= expireAtMillis`，到期瞬间即过期；`ttlMillis <= 0` 表示永不过期。
2. **回收时机**（确定性）：
   - 惰性：读命中已过期键时 CAS 回收，返回 `EXPIRED`；
   - 主动：每次写入前、显式调用 `purge-expired`、容量判定前，先回收全部已过期条目。
3. **容量按空间独立判定**：回收过期条目后所属空间仍放不下时，写入被拒绝并返回
   `CAPACITY_FULL`——只影响该空间的新写入，其它空间照常；**未过期数据绝不因容量
   被静默淘汰**。覆盖已有键不占新槽位，空间写满时仍可成功。
4. **状态可区分**：已被回收的过期键（物理删除）再访问返回 `NOT_FOUND`；
   已过期但尚未回收的键返回 `EXPIRED`。两者均可与彼此及 `OK` 明确区分。

## 持久化、恢复与容错边界

### WAL 格式

当前版本 v2（帧内携带空间名）：

```
文件头: MAGIC(3B 'CLW') + VERSION(1B = 2)
帧:    type(1B) | nsLen(4B) | keyLen(4B) | valueLen(4B) | expireAtMillis(8B)
      | CRC32(4B，覆盖前述字段与 ns/key/value 载荷) | ns(UTF-8) | key(UTF-8) | value(UTF-8)
```

- **v1 兼容与迁移**：v1 帧无 `nsLen/ns` 字段（固定区 21B）。打开 v1 文件时按旧布局
  恢复，全部记录归入默认空间 `default`，随后立即把有效记录以 v2 布局**原子重写**
  回原文件完成迁移；迁移前后数据语义不变，旧数据不丢失、可继续读写。
- **写顺序**：先追加 WAL 并 `fsync`，再改内存。WAL 写失败则内存不变，调用方收到异常。
- **删除**：仅对存活条目的显式删除写 DELETE 记录；过期回收不写 WAL
  （重放时过期 PUT 按当时时钟跳过，语义等价）。

### 崩溃恢复

- 启动时顺序校验每一帧；遇到**帧头不完整、帧体截断、类型/长度非法或 CRC 不匹配**，
  立即停止重放，并将文件**截断到最后一条有效帧之后**——损坏尾部被识别并忽略，
  **不导致启动失败，也不会读出脏数据**；截断后文件可继续正常追加。
- 重放语义：PUT 覆盖、DELETE 删除、已过期 PUT 跳过；每条记录按帧内空间名归位，
  重启后**各空间的数据、空间归属与占用与重启前一致**。恢复后某空间存活条目数超过
  其容量上限时保留全部已恢复数据（上限只约束新写入），并输出告警日志。
- **容错边界**：WAL 头（MAGIC/VERSION）损坏时判定为不可识别文件并重建为空日志
  （原数据视为全部丢失，属已声明的边界）；磁盘级故障（fsync 之后数据仍丢失）
  不在本引擎保证范围内。
- **压缩**：`compact()` 用当前存活快照原子重写 WAL（临时文件 + fsync + 原子替换），
  丢弃被覆盖/已删除/已过期的历史记录。

## 配置项

| 配置 | 默认值 | 说明 |
|---|---|---|
| `cache.max-entries` | 1024 | 每个空间的默认最大存活条目数；满且回收过期后仍放不下时，该空间写入返回 `CAPACITY_FULL` |
| `cache.namespace-capacities.<空间名>` | 无 | 指定空间的独立容量上限（覆盖默认值；允许为 0，表示该空间拒绝一切新键写入） |
| `cache.data-file` | `data/cache.wal` | WAL 数据文件路径（目录自动创建） |
| `cache.compact-on-startup` | false | 启动恢复完成后是否立即压缩 WAL |
| `server.port` | 0（随机） | HTTP 服务端口 |

## 兼容范围

- **API 兼容**：旧的 Java 构造器 `CacheEngine(int, Path, Clock)` 与全部不带空间的
  方法签名保留，语义不变（作用于默认空间）；旧 REST 请求体/路径无需修改。
- **数据兼容**：旧版 v1 WAL 文件启动时自动迁移为 v2，数据全部保留在默认空间；
  迁移后无法再被旧版本读取（单向迁移）。
- **统计语义**：`GET /api/cache/stats`（不带参数）返回全引擎聚合统计，其中
  `capacity` 字段保持旧语义（`cache.max-entries`）；各空间独立统计用
  `?namespace=` 获取。

## 测试

`src/test/.../tests/` 下 54 个用例，日志中打印输入、判定依据与恢复结果：

- `ExpiryBoundaryTest`：到期瞬间边界、NOT_FOUND/EXPIRED 区分、过期槽位回收、重启后过期键缺席；
- `CapacityEvictionTest`：容量满拒绝且不丢存活数据、覆盖不占槽位、批量写原子性、统计一致性；
- `ConcurrencyTest`：同键并发写无丢失更新、并发容量边界精确、读写线性化（无回退）、
  混合操作无死锁、并发写后重启完整恢复；
- `RestartRecoveryTest`：正常重启恢复、删除持久化、撕裂写尾部截断、CRC 损坏帧及之后数据忽略、
  冷启动、压缩后状态保持、多轮重启稳定；
- `CacheApiTest`：REST 端到端，404/410/507 失败原因可区分，批量操作逐键结果；
- `NamespaceIsolationTest`：跨空间同名键互不影响、删/改/批量/统计按空间隔离、
  旧 API 落入默认空间、空间名校验；
- `NamespaceCapacityTest`：空间写满只影响本空间、按空间容量覆盖（含容量 0 的确定拒绝）、
  超容量批量整体拒绝且不丢数据、本空间过期回收腾位、失败原因可区分；
- `NamespaceConcurrencyTest`：跨空间并发写无丢失更新且各空间计数精确、
  跨空间容量竞争边界精确、混合负载最终状态自洽（无死锁）；
- `NamespaceRestartRecoveryTest`：重启后各空间数据/归属/占用一致、跨空间损坏尾部忽略、
  v1 WAL 迁移入默认空间且二次重启稳定；
- `NamespaceApiTest`：REST 层空间参数（查询参数/请求体）、缺省空间旧行为不变、
  配置的空间容量生效（507）、批量与统计按空间隔离、空间列表。
