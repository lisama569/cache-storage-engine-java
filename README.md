# cache-storage-engine-java

基于 Spring Boot 的本地缓存存储引擎，支持 TTL、容量淘汰、并发访问与崩溃恢复，通过 REST API 对外提供服务。

## 一致性模型

- **线性化**：引擎所有公开操作（`get` / `put` / `remove` / `putAll` / `getAll`）在同一监视锁下执行，
  同一键上的更新、过期清理与淘汰构成全序，并发下不会出现丢失更新、计数漂移或死锁（单锁有序获取）。
- **写前日志**：每次变更先追加 WAL 并 `force` 落盘，再修改内存状态，保证崩溃后内存状态可从日志完整重建。
- **批量原子性**：`putAll` 先整体校验容量，任一不满足则全部不生效；成功时所有记录先落盘再统一生效。

## 过期与淘汰规则

- `ttlMillis <= 0` 表示永不过期；否则过期时刻为写入时刻 + TTL，`now >= expireAt` 即视为过期（边界含等于）。
- 过期采用惰性清理：访问到过期键时清理并返回 `EXPIRED`；`size()` 统计前会先清理过期条目，保证计数不漂移。
- 容量超限时按**确定顺序**淘汰：
  1. 先淘汰已过期条目；
  2. 再按 LRU（最久未使用）顺序淘汰。
- 淘汰是显式的既定策略；若淘汰全部现有条目仍放不下（如单条数据超过 `maxBytes`），
  写入返回 `CAPACITY_EXCEEDED`，**不静默丢弃任何未过期数据**，已有状态保持不变。

## 失败原因区分

| 状态 | 含义 | HTTP |
|---|---|---|
| `OK` | 成功 | 200 |
| `NOT_FOUND` | 键不存在（或已被淘汰/删除） | 404 |
| `EXPIRED` | 键存在但已过期 | 410 |
| `CAPACITY_EXCEEDED` | 容量不足且无法通过淘汰腾出空间 | 507 |

## 恢复与容错边界

- WAL 记录格式：`[type:1][keyLen:4][key][payloadLen:4][payload][crc32:8]`，CRC 覆盖记录全部前序字节。
- 重启时顺序回放，遇到**不完整记录或 CRC 不匹配**（异常终止留下的尾部）即停止，
  并将文件截断到最后一条完好记录末尾，随后从一致位置继续追加。
- 容错边界：最后一条完好记录之前的所有变更保证恢复；损坏点之后的记录（可能未完整落盘）被丢弃，
  不会导致启动失败，也不会读出脏数据。已落盘数据本身的物理损坏（非尾部）不在保证范围内。

## 配置项

| 配置 | 默认 | 说明 |
|---|---|---|
| `cache.max-entries` | 10000 | 最大条目数，`<=0` 表示不限制 |
| `cache.max-bytes` | 16777216 | 最大占用字节数（按 value 长度计），`<=0` 表示不限制 |
| `cache.data-dir` | `data` | WAL 持久化文件目录（文件名为 `cache.wal`） |

## REST API

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/cache/{key}` | 读取，返回原始字节 |
| `PUT` | `/cache/{key}?ttlMillis=` | 写入（请求体为原始字节） |
| `DELETE` | `/cache/{key}` | 删除 |
| `POST` | `/cache/batch?ttlMillis=` | 批量写入，请求体为 `{key: base64(value)}`，整体成功或整体失败 |
| `GET` | `/cache/stats` | 当前条目数与字节数 |

## 测试

```bash
mvn test
```

覆盖场景（测试日志会打印输入、判定依据与恢复结果）：

- `CacheEngineExpiryTest`：过期边界（边界前一毫秒命中、边界时刻过期）、`EXPIRED` 与 `NOT_FOUND` 区分、永不过期。
- `CacheEngineEvictionTest`：LRU 淘汰顺序、过期条目优先淘汰、超限写入拒绝且不丢数据、批量操作原子性。
- `CacheEngineConcurrencyTest`：多线程并发写无丢失更新与计数漂移、并发 put/remove 线性一致且限时完成（无死锁）、并发下不超容量上限。
- `CacheEngineRecoveryTest`：正常重启恢复、TTL 元数据恢复、截断尾部忽略、CRC 损坏记录忽略、空日志启动。
